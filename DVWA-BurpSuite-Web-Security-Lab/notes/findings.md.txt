DVWA + Burp Suite Web Security Lab — Findings

1. Purpose

The purpose of this exercise was to examine the behavior of DVWA's SQL Injection module at four security levels using normal and unexpected inputs.

Burp Suite was used to inspect HTTP requests and responses and to resend selected requests using Repeater.

All tests were performed against the local DVWA instance.

2. Low Security

Normal Input

- Input: "1"
- Observed result: First name "admin", surname "admin".

Single-Quote Input

- Input: "1'"
- Observed result: HTTP 500 Internal Server Error.
- Interpretation: The application returned a server error for this input. The available evidence does not establish the exact cause of the error.

Alphabetic Input

- Input: "abc"
- Observed result: HTTP 200, without the expected user information.

Finding

Different inputs produced different application responses. A server error is worth investigating, but it does not independently prove SQL injection.

3. Medium Security

Normal Inputs

The following results were observed:

Input| First Name| Surname
"1"| admin| admin
"2"| Gordon| Brown
"3"| hack| me
"4"| Pablo| Picasso
"5"| Bob| Smith

The normal IDs returned the corresponding records.

Alphabetic Input

- Input: "abc"
- Observed result: HTTP 500 Internal Server Error in Burp Repeater.

Single-Quote Input

- Input: "1'"
- Observed result: HTTP 500 Internal Server Error in Burp Repeater.

Finding

The application returned server errors for both unexpected inputs. The HTTP status alone does not identify the underlying cause or establish the effectiveness of the security controls.

4. High Security

Normal Inputs

The following results were observed:

Input| First Name| Surname
"1"| admin| admin
"2"| Gordon| Brown
"3"| hack| me
"4"| Pablo| Picasso
"5"| Bob| Smith

The High security interface used a separate session-input workflow. After submitting an ID and closing that interface, the corresponding record appeared on the main SQL Injection page.

Alphabetic Input

- Input: "abc"
- Observed result: HTTP 200, with no user details in the response.

Single-Quote Input

- Input: "1'"
- Observed result: HTTP 200, with no user details in the response.

Finding

The unexpected inputs did not return user details in the inspected responses. This observation does not, by itself, prove that SQL injection is prevented.

5. Impossible Security

Normal Input

- Input: "1"
- Observed result in the browser: First name "admin", surname "admin".

Repeater Test

- Observed result: HTTP 302 Found.
- Redirect destination: "index.php".
- Browser session: The normal SQL Injection page continued to work.

Finding

The browser successfully returned the expected record, but the Repeater request redirected to "index.php". The cause of the redirect was not conclusively established, so the Repeater test is recorded as inconclusive.

6. Burp Suite Observations

Proxy and HTTP History

Proxy and HTTP history were used to identify requests generated by the browser and inspect their methods, paths, parameters, and responses.

GET and POST Requests

The lab demonstrated that different application actions can use different HTTP methods. The High security workflow used a POST request to submit the ID.

Repeater

Repeater was used to resend selected requests and compare responses to different inputs.

A valid comparison depends on using the correct request, current session, parameters, and application security level.

7. Limitations

- Some unexpected-input tests returned errors or responses without user details, but the root causes were not independently confirmed.
- The Impossible security Repeater test redirected to "index.php" and could not be conclusively evaluated.
- HTTP status codes alone cannot prove whether an SQL injection vulnerability exists.
- The lab results describe the observed behavior of this local DVWA instance and should not be generalized to other applications.

8. Overall Conclusion

The exercise provided practical experience inspecting web requests, modifying inputs in Repeater, and comparing responses across DVWA's security levels.

The main learning outcome was the importance of interpreting request context and response content together. Reliable security conclusions require repeatable tests and evidence that directly supports each claim.
