DVWA + Burp Suite Web Security Lab

Overview

This project documents a hands-on web application security testing lab using Damn Vulnerable Web Application (DVWA) and Burp Suite Community Edition.

The purpose of the lab was to understand how a web application responds to different inputs and compare its behavior across DVWA's four SQL Injection security levels: Low, Medium, High, and Impossible.

All testing was conducted against a locally hosted DVWA instance in a controlled lab environment.

Objectives

- Set up and access DVWA locally.
- Configure Burp Suite to inspect HTTP requests and responses.
- Understand GET and POST requests.
- Use Burp Proxy and HTTP history to observe browser traffic.
- Use Burp Repeater to resend requests and compare responses.
- Test normal and unexpected inputs in the SQL Injection module.
- Compare application behavior across four security levels.
- Document findings and retain supporting evidence.

Tools and Technologies

- Kali Linux
- Damn Vulnerable Web Application (DVWA)
- Burp Suite Community Edition
- Web browser
- HTTP and HTTPS concepts
- SQL Injection testing concepts

Lab Environment

DVWA was accessed locally at:

"http://127.0.0.1:42001"

The application was tested in a controlled environment. No external systems were targeted.

Testing Methodology

1. Application Setup

Started DVWA and accessed its login page. After logging in, confirmed that the application dashboard and SQL Injection module were accessible.

2. Burp Suite Configuration

Opened Burp Suite and its built-in browser. Used Proxy and HTTP history to inspect requests generated by interactions with DVWA.

3. Request Inspection

Inspected HTTP requests and responses, including GET and POST requests. Used Burp Repeater to resend selected requests and compare the application's responses to different inputs.

4. SQL Injection Module

Tested the SQL Injection module at the following DVWA security levels:

- Low
- Medium
- High
- Impossible

Normal numeric inputs were tested alongside selected unexpected inputs, including alphabetic input and a single quote.

5. Evidence Collection

Captured screenshots of the application, Burp Suite configuration, selected requests, and test results. Supporting evidence is stored in the "evidence/" directory.

Summary of Observations

Security Level| Observations
Low| ID 1 returned the admin record. A single-quote test returned HTTP 500.
Medium| Normal IDs returned the expected records. Alphabetic and single-quote tests returned HTTP 500 in Repeater.
High| Normal IDs returned the expected records. Alphabetic and single-quote tests returned HTTP 200 without user details in the response.
Impossible| ID 1 returned the admin record in the browser. The Repeater request redirected to "index.php" with HTTP 302, so that Repeater test was inconclusive.

These results describe observed behavior. HTTP status codes alone do not establish whether SQL injection is possible or whether a security control is effective.

Key Learning Outcomes

- Understood how Burp Suite Proxy and HTTP history help inspect application traffic.
- Practised sending requests to Burp Repeater for controlled testing.
- Learned to identify differences between GET and POST requests.
- Observed how application responses can vary depending on the input and configured security level.
- Learned that HTTP status codes must be interpreted alongside response content and request context.
- Practised documenting security testing results without overstating conclusions.
- Gained experience organizing evidence for a cybersecurity portfolio.

Scope and Ethics

This project was performed against a locally hosted, intentionally vulnerable application for educational purposes.

Testing was limited to the controlled lab environment. The techniques demonstrated here should only be used on systems for which explicit authorization has been granted.

Conclusion

This lab provided practical experience inspecting HTTP traffic and comparing application behavior under different security configurations. It also reinforced the importance of validating observations, understanding session context, and documenting limitations accurately.
